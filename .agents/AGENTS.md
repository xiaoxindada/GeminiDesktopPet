# Git 管理规则
1. 生成或执行 git 提交时，始终遵守以下提交信息格式：
```text
50 字符以内的改动摘要

详细说明为什么做这次改动、解决了什么问题。正文中的每一行
最多 72 字符。

Assisted-by: <当前模型的代号名称>
```
- **标题行**：50 字符以内的改动摘要。
- **空行**：标题行与正文之间用一个空行分隔。
- **正文**：详细说明为什么做这次改动、解决了什么问题。正文中的每一行最多 72 字符。
- **尾注**：在提交信息正文末尾附上 `Assisted-by: <当前模型的代号名称>` 尾注 新会话读取一次 例 `Assisted-by: GPT-6 Astra`, `Assisted-by: Claude Opus 5.5, Gemini 4 Carbon`
2. **禁止未经允许不要 push**：永远不要在用户不允许的情况下 push 任何本地提交，除非用户明确指定。
3. **提交前保持标准格式化**：代码提交 git 时需要保持标准格式化。
4. **提交必须按职责拆分**：禁止将多个不相关的改动打包在同一次提交中；按功能或修复职责合理区分拆分，同一职责内相互配套的改动可合并提交。
5. **发布新版本（Tag + Release）**
   - 运行 `BuildRelease.bat --no-pause` 打包出 `out\GeminiDesktopPet-<tag>-win-x64.zip`。
   - 创建并推送 Tag 后，汇总描述(AI)自行对比和上个版本的差异, 用简洁的描述整理修改历史后，通过 `gh release create` 发布到对应 Tag 的 GitHub Release；若 Release 已存在则用 `gh release upload --clobber` 与 `gh release edit` 更新。
   - Release 说明末尾必须附 Full Changelog 一并发布。

# 隐私与敏感信息规范
1. **编写或修改代码时禁止生成带有敏感数据的代码**：此规则适用于整个开发过程，无论是否提交、推送或发布；禁止在源代码、示例、注释和测试数据中写入真实或未脱敏的密钥、令牌、密码、个人信息及其他敏感数据，需要示例时使用明确的占位符或脱敏数据。
2. **推送与提交时禁止生成或包含敏感数据**：编写代码、文档、注释、测试、预览图以及执行提交、推送或发布 Release 时，严禁生成、写入或推送任何真实或未脱敏的敏感数据（如 API Key、Token、账号邮箱、密码凭据、真实账户额度数据、含本机用户名的绝对路径，以及本地配置文件或运行日志产物）。
3. **禁止生成或推送敏感描述**：在 `README.md`、更新日志、Release 说明与公开文档中，禁止暴露敏感配置字段键名、内部鉴权实现、内部 CLI / 进程探测与缓存文件细节或未公开的敏感技术描述；如涉及问题反馈指引，须提醒用户先脱敏后再提交。
4. **发布前自检**：发布 Release 前，必须确认工作区、变更内容与产物附件中均不包含上述敏感数据与敏感描述。

# 代码注释规则
1. **重要逻辑必须写注释**：编写或修改代码时，对重要、核心或复杂的逻辑始终添加清晰的注释。
2. **不要逐行加注释**：改代码时无需每一行都加注释，只有在重要或者很复杂的逻辑上才加。
3. 代码注释要用简洁语言阐述 重要部分或复杂算法注释才需要详细。

# 开发完成后测试规则
1. **优先以最小化测试为主**：开发完成后优先运行与本次改动直接相关的最小必要测试，避免为样式、文案、坐标位置、素材替换、菜单/页面细节或交互微调等小改动盲目新增回归测试，也无需每次改动都执行全量测试。
2. **按需补充验证**：仅在涉及核心逻辑、跨模块改动或较高回归风险时，按需补充或运行对应范围的测试；无需自动化测试的小改动可直接交付，并简明说明验证方式。
3. **OAuth 仅允许用户手动测试**：禁止新增、保留或执行 OAuth 自动化测试，包括模拟授权、浏览器登录、回调、授权码兑换、凭据刷新、登录检测及授权后的模型获取测试。涉及 OAuth 的改动仅做静态代码检查，交付时通知用户自行验证，不得把模拟结果当作真实授权成功。

# 联网对话实现规则
1. **只支持官方 API Key**：联网聊天与模型获取仅通过用户填写的 Gemini API Key 调用 Google 官方接口。不得恢复 OAuth 授权、浏览器登录、本地凭据发现或 CLI 聊天通道。
2. **禁止反向代理实现**：不得使用反向代理、中转服务或内部接口实现聊天与模型获取。
3. **禁止 OAuth 实现**：禁止加入 OAuth 授权代码相关代码。
